别听我们说：打开开发者工具，盯着“网络”面板，拖一张图片进来。没有任何一个请求带着图片、缩略图、文件名，或者你选中内容的一个字节。或者干脆拔掉网线，照样编一张试试。

这个说法要怎么验证

  • 你的图片没有地方可去。Content-Security-Policy 列出了这个页面被允许联系的每一个地址，其中没有一个属于本站。这里不存在能收集你文件的接口，代码里也没有任何一处会去发送它们，哪怕真有这么个接口。
  • 这里没有任何东西会去取什么。src/ 里没有 fetch，没有XMLHttpRequest，也没有 sendBeacon。编码用的是btoa 和 encodeURIComponent — 浏览器从一开始就有的两个函数，它们接收字节、返回文本，哪儿也不去。
  • 预览本身就是证据。每个结果旁边那张图，是从这个页面刚刚拼出来的 data URI 画出来的，不是从你的文件画的。它能显示，说明这个 URI 是对的，就在你的机器上，没有服务器参与 — 而如果它显示不出来，页面会照实说，而不是把一个坏东西塞给你。
  • 元数据提醒是站在你这边的。data URI 是原样复制文件，所以一张照片的 GPS 定位会跟着它一起进到你的样式表里。这个页面会读出里面有多少这类东西并告诉你，因为另一种可能是：你在它已经被提交之后才发现。
  • Google 加载了什么，又拿不到什么。广告脚本和统计脚本来自 Google，捐助按钮来自 Buy Me a Coffee。它们没有一个被交给过任何关于你图片的信息。每一行读取或编码文件的代码，都由这个源提供，也都列在仓库里。
  • 它可以离线使用。断开网络，这个工具毫无变化，因为它里面从来就没有过一个联网的步骤。这是所有证明里最简单的一个。

你可以自己核对。以上没有一条需要你凭信任接受。这个页面是由 仓库里的模板和配置，经过一个你可以阅读、也可以自己运行的构建脚本生成的， 结果提交在 dist 分支上 — 所以你可以把实际提供的内容， 和从源码构建出来的结果直接做比对：

      怎么把一张图片变成 data URI

      1. 选择你的图片。把它们拖到选择框上，或者手动挑。浏览器直接从你的硬盘上读它们；这个过程中没有任何东西被送去哪里。
      2. 说明结果要用在哪儿。光要 URI，还是要一条 CSS 规则、一个自定义属性、一个<img> 标签，或者 Markdown。每一种都会给 URI 加上引号，而正是这个细节决定了一个内联的 SVG 是能用，还是悄无声息地不能用。
      3. 看清它花了多少。每个结果都会说明它变成了多少个字符、比原文件大了多少，以及这个体积的东西值不值得内联。base64 会多出三分之一；这三分之一换不换得回一次省下的请求，完全取决于体积，所以页面会告诉你你落在这条线的哪一边。
      4. 看一眼那些提醒。如果图片带着 EXIF、色彩配置或 XMP，它会被点名，并附上它占了你结果里多少字节。如果扩展名和实际格式对不上，页面会按实际格式来，并告诉你。如果你的浏览器画不出这个结果，它也会说。
      5. 复制，或者下载。每个结果一个按钮，还有一个把全部一次拿走 — 自定义属性会被包在一个 :root 块里出来，可以直接粘到样式表最上面。

      常见问题

      我的图片会被上传到什么地方吗？

      不会。文件由你自己的浏览器、在你自己的硬件上读取和编码，用的是浏览器本来就有的两个函数。这个工具没有任何形式的网络功能 — 它从不取任何东西，也从不发任何东西 — 而页面的Content-Security-Policy 列出了它可能联系的每一个地址，其中没有一个属于本站。

      data URI 是什么？

      它是一种把整个文件写在本该放网址的位置上的写法。不写url("logo.png") —— 那是让浏览器去取点什么 —— 而是写url("data:image/png;base64,iVBORw0...")，里面装着图片本身。浏览器当场把它解出来。实际效果是少一次请求：图片和样式表或者页面一起到，而不是在它们之后才到。

      我的 SVG 为什么不是 base64？

      因为对它来说 base64 是错的编码。SVG 是文本，而 URL 本来就能装文本 — 只有少数几个字符需要转义。把这几个做百分号编码、其余原样留下，得到的 URI 通常比同一个文件的 base64 短五分之一，而且你在样式表里还读得懂它：元素名、颜色和 viewBox 都还在那儿，随时可以改。有一个勾选框可以强制用 base64，给那些非要不可的工具链。

      base64 会让我的图片大多少？

      大约三分之一。文件里三个字节变成四个 base64 字符，也就是 33%，这还没算前面那段 data:image/png;base64,。这是下限，而且无法避免：这就是用 URL 允许的那些字符去写任意字节所要付的代价。这也是为什么页面会把字符数摆在文件大小旁边，而不是让你等样式表上线之后才发现。

      什么时候内联一张图片才真的划算？

      当它很小、而且马上就要用的时候。一个每个页面都会加载的样式表里放一个 2 KB 的图标，是明显划算的：少一次往返，而且 CSS 一到位图片就在。过了大约 10 KB，这笔交易就反过来了。内联的图片不再是一个独立文件，所以它没法被单独缓存，没法和别的东西并行下载，而且外面那个文件一变，它就要被完整地重新下载一遍 — 样式表里一张 200 KB 的照片，就是给全站每个页面的关键路径上加了 200 KB。页面会告诉你每个结果落在这条线的哪一边。

      gzip 能把 base64 多出来的部分抵消掉吗？

      比大家想的要少。已经压过的文件 — PNG、JPEG 和 WebP 都是 — 再做 base64，压缩效果很差，因为压缩器几乎找不到剩余的冗余了；通常你能拿回来的只是 base64 多出的那三分之一里的十分之一左右，不是全部。百分号编码的 SVG 恰好相反：它还是文本，所以压缩率和之前差不多，这又是一条不该给它上 base64 的理由。

      这会不会改动我的图片？

      不会，而且这是和这里大多数工具刻意不同的一点。没有任何东西被解码成像素再编码一遍：从你硬盘上读出来的字节，就是进到 URI 里的字节。一个 JPEG 还是原来那个 JPEG，质量一样，尺寸一样。正因为如此，结果可以说是同一个文件，而不是它的一份副本。

      那我的 EXIF 和 GPS 数据也会进到样式表里？

      会，而且这正是你在粘贴之前值得想一想的地方。因为什么都不重新编码，相机写下的一切都跟着图片走：位置、时间戳、相机的序列号。在一张手机照片上这可能占到文件的 30 KB，在你页面的关键路径上就变成 40 KB 的 base64，而且是一个即将被提交进代码仓库的家庭住址。这个页面会读出 JPEG、PNG 或 WebP 里有多少元数据并告诉你。想先把它们拿掉，用EXIF 查看与清除。

      它为什么用了和我文件扩展名不一样的类型？

      因为扩展名可能是错的，字节不会。一个名叫 logo.png、其实是按 JPEG 导出的文件常见到每个图片工具都得应付，而一个声明了错误类型的 data URI 干脆就画不出来 — 没有回退，也没有一条值得一读的错误信息。所以类型是从文件开头那几个字节读出来的，这里涉及的每一种格式里那几个字节都说得毫不含糊，而当两者不一致时，页面会告诉你。

      预览是空白的，出什么问题了？

      大概率不是 URI 的问题。HEIC 和 TIFF 都能生成完全合法的 data URI，但除了 Safari 没有哪个浏览器画得出来，所以你粘到哪儿它都是缺的 — 先用图片压缩或者图片缩放把它转成 PNG、JPEG 或 WebP。如果格式很普通，那多半是文件本身坏了：预览是从这个页面拼出来的 URI 画的，画不出来就说明画面没能解码。

      data URI 有大小上限吗？

      在 CSS 里和 <img> 标签里，你碰不到一个上限；现代浏览器在那儿没有什么实际的封顶。浏览器确实限制的是往地址栏里输入 data URI，现在大多数浏览器对稍微复杂一点的都会拒绝，理由是安全，和这里的用法无关。真正的限制是上面那条：远在任何技术上的东西崩掉之前，那个页面就已经比用一个普通图片文件时更慢了。

      它免费吗，需要注册吗？

      免费，而且没有账号、没有登录、没有试用期、没有水印。文件的数量和大小也没有上限，因为没有一台服务器在为它们付钱 — 活是在你自己的机器上干的。本站带广告，这就是它的经费来源；广告拿不到任何关于你图片的信息。

      断网能用吗？

      能。把页面加载一次，然后断开网络，它照样工作。这也是证明“什么都没被上传”最简单的办法：一个把你的图片送出去编码的工具，在你拔线的那一刻就会停下来。
