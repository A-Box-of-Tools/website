这条隐私承诺怎么核实

  • 你的图片没地方可去。Content-Security-Policy 把这个页面允许联的地址全列了出来，没有一个是本站的。这里没有能收文件的接口，代码里也没有一行会把文件发出去，就算真有那么个接口也一样。
  • 这里没有任何东西会去联网取数据。整个 src/ 里，一个 fetch、一个XMLHttpRequest、一个 sendBeacon 都找不到。编码就是 btoa 和 encodeURIComponent，浏览器从一开始就带着的两个函数，进去是字节，出来是文本，哪儿也不去。
  • 预览图本身就是凭据。每个结果旁边那张图，是拿这个页面刚生成的 data URI 画出来的，不是拿你的文件画的。它能显示，说明这串 URI 是对的，而且是在你的机器上、没有服务器掺和的情况下对的。要是显示不出来，页面会直说，不会塞给你一个坏的。
  • 那条元数据提醒，是站在你这边的。data URI 是把文件原样抄一遍，所以一张照片的 GPS 定位会跟着一起进你的样式表。这个页面把里面有多少这种东西读出来告诉你，不然你就得等它提交进仓库之后才发现。
  • Google 加载了什么，又拿不到什么。广告脚本和统计脚本来自 Google，捐助按钮来自 Buy Me a Coffee。关于你图片的信息，一条都没给它们。读文件、做编码的每一行代码都从本站发出，也都摆在仓库里。
  • 断网照样能用。断开网络，这个工具跟原来一模一样，因为它本来就没有联网这一步。这是最省事的一条证明。

      图片怎么转成 data URI
      1. 选好你的图片。拖到下面的方框里，或者点开自己挑。浏览器直接从你的硬盘上读，这期间没有东西发出去。

      3. 看看代价有多大。每个结果都写明它变成了多少个字符、比原文件大出多少，以及这么大的东西内联进去到底合不合算。base64 会多出三分之一，这三分之一值不值一次省下的请求，完全看文件多大，所以页面直接告诉你落在界线的哪一边。

      常见问题

      我的图片会传到什么地方去吗？

      不会。读取和编码都由你自己的浏览器在你自己的硬件上完成，用的是浏览器早就有的两个函数。这个工具没有任何联网功能，不取东西，也不发东西。页面的 Content-Security-Policy 把它可能联的地址全列了出来，没有一个是本站的。

      data URI 是什么？

      一种把整个文件写在“本该写网址的地方”的办法。原来写url("logo.png")，浏览器就得跑一趟去取；改写成url("data:image/png;base64,iVBORw0...")，图片本身就在这串字里，浏览器当场解出来。实际效果是少一次请求，图片跟着样式表或者页面一起到，而不是等它们到了之后再去取。

      为什么我的 SVG 没走 base64？

      因为 base64 对它来说是错的编码。SVG 本身是文本，而网址本来就能装文本，只有少数几个字符需要转义。把那几个转成百分号写法、别的原样留着，生成的 URI 通常比同一个文件的 base64 短五分之一左右，而且在样式表里还看得懂，元素名、颜色、viewBox 都还在，随手能改。个别工具链非要;base64 不可，页面上有个勾选框可以强制。

      base64 会让图片大多少？

      大约三分之一。三个字节的文件变成四个字符的 base64，也就是 33%，前面还要再加上 data:image/png;base64, 这一截。这是底线，躲不掉，用网址允许的那些字符去表示任意字节，代价就是这么多。也正因如此，页面把字符数摆在文件大小旁边，省得你等样式表都发布了才发现。

      什么时候内联图片才真的划算？

      又小又必须马上出现的时候。每个页面都要加载的样式表里放一个 2 KB 的图标，这是明摆着的赚：少一次往返，CSS 一到图就在。过了大约 10 KB，这笔账就翻过来了。内联进去的图片不再是一个独立文件，没法单独缓存，没法跟别的东西并行下载，而且外面那个文件一改，它就得整个再下一遍。样式表里塞一张 200 KB 的照片，等于给全站每个页面的关键路径都加了 200 KB。每个结果落在界线的哪一边，页面会告诉你。

      gzip 能把 base64 多出来的那部分压回去吗？

      没大家想的那么灵。base64 编的要是本来就压过的文件，PNG、JPEG、WebP 都是这种，压出来效果很差，因为里头几乎没有冗余留给压缩器去找了。通常也就找回 base64 多出来那三分之一里的十分之一，绝不是全部。百分号编码的 SVG 正好相反，它还是文本，压缩效果跟原来差不多，这也是不该给 SVG 上 base64 的又一个理由。

      这一步会动我的图片吗？

      不会，而且这一点跟这里多数工具是刻意不同的。没有哪一步把它解码成像素再编回去，从你硬盘上读出来的字节，就是进 URI 的那些字节。JPEG 还是原来那个 JPEG，画质一样，尺寸一样。也正因为如此，结果可以说就是同一个文件，而不是它的一份副本。

      那 EXIF 和 GPS 也一起进样式表了？

      是的，而这正是粘出去之前值得想一想的地方。因为什么都不重新编码，相机写下的东西全都跟着画面走：位置、时间戳、机身序列号。手机照片里这些能占到 30 KB，编成 base64 就是 40 KB 压在你页面的关键路径上，同时还把一个家庭住址提交进了仓库。JPEG、PNG 和 WebP 里到底带了多少元数据，页面会读出来告诉你。想先清干净，用EXIF 查看与清除。

      为什么它用的类型跟我的扩展名不一样？

      因为扩展名可能是错的，字节不会。一个叫 logo.png、其实是按 JPEG 导出的文件，常见到每个图片工具都得应付。而一个类型声明错了的 data URI 根本不显示，没有兜底，也没有一句值得看的报错。所以类型是从文件开头那几个字节读出来的，这里涉及的每种格式，开头都说得毫不含糊。两边对不上时，页面会告诉你。

      预览是空白，哪儿出问题了？

      多半不是 URI 的问题。HEIC 和 TIFF 都能生成完全合法的 data URI，可除了 Safari 没有浏览器画得出来，所以你粘到哪儿它就在哪儿缺一块。先用图片压缩或者图片缩放转成 PNG、JPEG 或 WebP 再说。要是格式本来就很普通，那多半是文件本身坏了：预览是拿这个页面生成的 URI 画的，画不出来，就说明这张图没能解码。

      data URI 有长度上限吗？

      在 CSS 里和 <img> 标签里，你碰不到什么上限，现在的浏览器在这两处基本没有实际限制。浏览器真正限制的是把 data URI 打进地址栏，稍微长一点的现在多半直接拒绝，那是出于安全考虑，跟这里的用法没关系。真正的限制是上面那条：早在技术上出问题之前，你这个页面已经比老老实实放张图片更慢了。

      免费吗？要注册吗？

      免费，没有账号，不用登录，没有试用期，也没有水印。文件的数量和大小同样没有上限，因为没有哪台服务器在为它们掏钱，活是在你自己的机器上干的。本站带广告，经费就是这么来的，广告拿不到关于你图片的任何信息。

      断网能用吗？

      能。页面开一次之后断网，它照干不误。这也是证明“什么都没上传”最省事的办法。一个把图片送出去编码的工具，拔线那一刻就停了。
