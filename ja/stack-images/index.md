# 画像スタック｜連写をまとめる、RAWも含めて

20枚を1枚に。20回のアップロードもRAW現像ソフトもなしで。

> 連写した写真を1枚にまとめます。平均でノイズを消し、中央値で場面から人を消し、比較明で星の軌跡にし、あるいはマクロ撮影を深度合成します。CR2・NEF・ARW・DNG・RAF・CR3は、カメラ自身のプレビューを取り出して読みます。すべてブラウザの中で動きます。

このページは、ブラウザの中だけで動く対話型のツールです（https://abox.tools/ja/stack-images/）。渡したものが送信されることはありません。以下は、このページがツールについて言葉で説明している内容のすべてです。使うには、このアドレスを開いてください。

## 写真が**アップロードされることはありません**。サーバーが存在しないからです。

各フレームを開き、デコードし、位置を合わせ、合成し、書き出す処理は、すべて手元のブラウザが手元の端末で行います。60 MBのRAWファイル20枚はおよそ1ギガバイトの写真ですが、その1バイトも動きません。この道具にはネットワーク機能がそもそもなく、ファイルは送り先を持たないworkerがディスクから直接読みます。

- ✗ アップロードなし
- ✗ アカウント不要
- ✗ 透かしなし
- ✓ RAWを読む
- ✓ オフラインで動く
- ✓ オープンソース

## ブラウザで写真をスタックする方法

1. **フレームを選びます。** 連写でも、段階露光の一組でも、インターバル撮影の並びでも、RAWファイルの入ったフォルダでもかまいません。届いた順に1枚ずつ開き、その行が何が出てきたかを書きます。RAWファイルならカメラ、中で見つかったプレビューの大きさ、そしてそれを見つけるのにファイルをどれだけ読まずに済んだかです。
2. **何を失いたいのかに合う手法を選びます。** ノイズなら平均、何かが動いていたならシグマクリッピングです。人や車や通り過ぎる飛行機なら中央値。暗い空を星の軌跡にしたいなら比較明。フォーカスリングを回しながら撮ったマクロなら深度合成です。メニューの下の説明が、あなたの枚数に対して各手法が何をするのかを書きます。
3. **フレームの位置合わせが要るか決めます。** 手持ちなら、はい、平行移動だけ。手持ちで向きも変えていたなら、平行移動と回転と拡大縮小。固定した三脚やインターバル撮影ならいいえで、そのほうが速くなります。各フレームは基準と付いたフレームに対して測られます。何も言わなければ先頭の一枚が基準で、「これを基準にする」は印を移すだけで、並び順は置いたままです。
4. **4つの数字を読んでから、ボタンを押します。** 何かが走り出す前に、ページが結果の大きさ、おおよそのメモリ使用量、フレームを何回デコードするか、ファイルをどれだけ読んだかを書きます。一組が一度にメモリへ収まらなければそう書きますし、どの作業解像度なら収まるのかも書きます。

## 詳しい解説

[ノイズを減らす、あるいは人を消すために写真をスタックする方法](https://abox.tools/ja/guides/stack-photos-to-reduce-noise/): スタックは連写した複数のフレームを1枚にまとめます。どの手法を使うかは、何を失いたいかによります。ノイズか、通行人か、マクロの浅い被写界深度か。それぞれの仕組みと費用、そしてRAWファイルがどこに収まるのか。

## よくある質問

### 写真はどこかへアップロードされますか。

いいえ。各フレームを開き、デコードし、位置を合わせ、スタックし、書き出す処理は、すべて手元のブラウザが手元のハードウェアで行います。この道具にはネットワーク機能がそもそもなく、何かを取りに行くことも送ることもありません。ページの`Content-Security-Policy`には接続しうるアドレスがすべて書かれていますが、そのどれもこのサイトのものではありません。ページを一度読み込んで回線を切っても、そのまま動きます。ここでそれがほかの道具より効いてくるのは、単に量のせいです。RAWフレーム20枚はおよそ1ギガバイトで、その平均を取ってもらうために1ギガバイトの写真をアップロードすることこそ、この道具が避けるためにある事柄です。

### どのRAW形式を読めますか。どうやって読むのですか。

CR2、CR3、NEF、NRW、ARW、SR2、SRF、DNG、ORF、RAF、RW2、PEF、SRW、3FR、IIQ、DCR、KDC、MRW、MEF、RWLなど、カメラが書くもののほとんどです。そこから読むのは、撮影のときにカメラ自身が現像した原寸のJPEGプレビューです。カメラの背面に映るあの画像であり、OSがサムネイルとして描くあの画像です。ファイルのディレクトリ構造をたどって見つけますが、それは数キロバイトの読み取りが数回で済み、そのあと1か所を取り出すだけです。**センサーデータのデモザイクではありません。**結果にはカメラのホワイトバランスとピクチャースタイルが入り、1チャンネル8ビットです。RAW現像ソフトが渡す12ビットや14ビットの線形なセンサーデータではありません。

### ではなぜセンサーデータをきちんとデコードしないのですか。

LibRawかdcrawを同梱することになるからです。ひとつの形式の系統のためだけに数十メガバイトの2つめのエンジンを抱えることになり、その大半はメーカーごとの圧縮方式です。その取引はこのサイトのソースの`docs/what-can-be-built-here.md`で論じられていて、カメラRAWはこの道具ができる前から除外一覧に載っていました。変わったのはその問いへの答えではなく、スタックにはそれが要らないと分かったことです。プレビューは原寸ですし、どのみちカメラがJPEGとして渡していた画像そのものですし、それを読むのはデモザイクのおよそ100倍速いのです。センサーデータが要るなら、先にRAW現像ソフトで現像して、そこから出たTIFFやJPEGをスタックしてください。この道具はそれも受け取ります。

### 何枚まで、どのくらいの大きさまで扱えますか。

7つの手法のうち6つは流しながら処理します。累算器をひとつ持ち、各フレームをちょうど一度だけ読むので、100枚でも2枚と同じメモリで済み、増えるのは時間だけです。中央値だけが例外で、ある集合の真ん中の値は全部そろうまで分からないため、すべてのフレームを同時に抱えます。2400万画素20枚でおよそ1.4 GBになり、それを渡してくれるブラウザはありません。そうなったときは画像を横帯に切り、1帯ずつスタックしますが、帯ごとにフレームを読み直す分の費用がかかります。ページはこれをすべてボタンを押す前に計算して数字で見せるので、遅い実行が驚きになることはありません。

### フレームの位置合わせは実際に何をしているのですか。

各フレームが基準の1枚に対してどれだけずれたかを求め、そのぶん戻します。1画素の何分の1という精度です。手法は位相相関です。2枚の画像のあいだのずれは、2つのスペクトルのあいだの位相差として現れるので、それぞれ1回のフーリエ変換で、200画素のずれも2画素のずれと同じ安さで見つかります。2つめの設定は、同じ手を対数極座標のスペクトルに当てて回転と拡大縮小も取り戻します。どれも大域的で、フレーム全体に対してずれが1つ、角度が1つ、倍率が1つです。ですから動いたカメラは直せますが、動いた被写体は直せませんし、一歩左から撮った写真も直せません。目に見える結果もひとつあります。左へ20画素動かしたフレームはもう右端に届かないので、結果はすべてのフレームが覆う範囲まで切り詰められます。位置を合わせたスタックが元のフレームよりわずかに小さく返るのはそのためで、そこになかったフレームでできた黒い縁を避ける唯一の方法でもあります。

### どの手法を使えばいいですか。

何も動かなかった一組のノイズには**平均**です。ランダムなノイズを、枚数の平方根ほど減らします。一部の時間だけそこにあったものを消すなら**中央値**で、混み合った広場を十数回撮って無人の広場を得るという古典的な使い方がそれです。両方が欲しいなら**シグマクリッピング**で、各画素がふだん何であるかを学んでから、それと合う値だけを平均するので、通り過ぎる車に対する中央値の強さと、平均のノイズ低減をあわせて得られます。星の軌跡や花火やライトペインティングには**比較明**。動いた明るいものを消すなら**比較暗**。1回の長時間露光を真似るなら**加算**。フォーカスリングを回しながら撮ったマクロには**深度合成**です。

### RAWファイルは14ビットなのに、結果がなぜ8ビットなのですか。

スタックされているのがカメラ自身のプレビューで、それがJPEGだからです。ただしスタックがその代償の一部を取り戻すことは言っておく価値があります。8ビットのフレーム16枚の平均は、そのどの1枚よりも本当に細かい階調を持ちます。各フレームの丸め方を違わせていたノイズこそが、平均を段と段のあいだに落ち着かせるからです。ここでの計算は浮動小数点で行い、いちばん最後に一度だけ丸めるので、途中で捨てられるものはありません。それでも線形なセンサーデータをスタックするのとは違いますし、この道具はそのふりをしません。

### 大きさの違うフレームや、別のカメラのフレームをスタックできますか。

できますが、たいていは間違いですし、そのつもりだったか確かめる価値があります。結果はいちばん大きいフレームの大きさになり、ほかのフレームはそこに収まるよう拡大縮小されて中央に置かれます。カメラを混ぜると色の解釈も混ざるので、2つの平均は同じ光に対する2つの違う解釈の平均になります。本当に役に立つのは、2つの解像度で撮った一組や、同じ場面のRAWファイルとJPEGです。

### 実行が帯に分かれると出ました。どういう意味ですか。

その手法に必要な作業メモリが、この道具が一度に確保しようとする量を超えているという意味です。ですから画像を横帯に切り、1帯ずつスタックします。結果はまったく同じものになります。ただ帯ごとにフレームを読み直すので時間がかかりますし、それが何回のデコードになるのかをページが書きます。作業解像度を1段下げるとメモリは4分の1になり、帯に分かれる実行はほぼいつも一度きりの実行に戻ります。どの設定ならそうなるのかも説明に出ます。

### ほかの道具はWorkerを使っていないのに、これだけ使うのはなぜですか。

処理が分単位で測られる唯一の道具だからです。ここのほかの道具は1、2秒で終わることをしていて、そこで処理をメインスレッドの外へ出すのは儀式にすぎません。大きなフレーム20枚をスタックするのは数百メガバイトにわたる密な計算で、メインスレッドではそれは固まったページを意味します。進捗バーは動かず、中止ボタンは応じず、しまいにはブラウザがタブを閉じようかと言ってきます。Workerはこの同じブラウザの中の2本目の流れで、この同じフォルダのファイルを、この同じポリシーの下で動かします。サーバーでもネットワーク機能でもありません。

### 無料ですか。アカウントは必要ですか。

無料で、アカウントもログインも試用期間も透かしもありません。何枚スタックするかにも、それがどれだけ大きいかにも制限はありません。その費用を払うサーバーがないからです。処理は手元の端末で起こり、天井は手元のメモリだけです。このサイトは広告で運営されていて、広告側にはあなたの写真について何も渡されません。

## この主張を確かめる方法

- **写真には出ていく先がありません。** Content-Security-Policyには、このページが接続しうるアドレスがすべて書かれていて、そのどれもこのサイトのものではありません。ファイルが集まりうるエンドポイントはここにはなく、あったとしても送るコードがありません。`src/`にもworkerにも、`fetch`も`XMLHttpRequest`も`sendBeacon`もありません。
- **RAWファイルは読まれるだけで、送られませんし、読まれる量もごくわずかです。** カメラのRAWファイルには、撮影のときにカメラ自身が現像した原寸のJPEGがすでに入っています。この道具はディレクトリのエントリをいくつかたどってそれを見つけ、そのあと1か所だけを求めます。60 MBのファイルでもたいてい100キロバイト未満です。作業中、ページはその数字をファイルの大きさと並べて見せ続けます。センサーのデータはそもそも一度も読みません。
- **処理はサーバーではなく、この端末のWorkerで動きます。** ここでworkerを使う道具はこれだけです。スタックは秒ではなく分の計算で、固まったページは進み具合を見せることも中止されることもできないからです。Workerはこの同じブラウザの中の2本目の流れです。`src/worker.js`を見てください。そこにはファイルそのものが渡されますが、ファイルへの参照はバイト列ではないので、それは無料です。そしてページとまったく同じContent-Security-Policyの下にあります。つまり送り先がありません。
- **この一組について、どこにも報告されません。** 何枚スタックしたか、どのカメラが書いたか、それぞれがどれだけずれていたか、どの手法を選んだか、どれだけ時間がかかったか。それらは閉じるまでこのページのメモリにあるだけです。このリポジトリにはその内容を運ぶ独自の分析イベントはありませんし、ダウンロードのあとにこのサイトが尋ねる唯一の質問は、親指の向きと道具の名前を送るだけで、ほかには何も送りません。
- **オフラインで動きます。** 回線を切っても道具は変わりません。もともとネットワークの段階がなかったからです。workerとそれが読み込むすべてのモジュールはこのページ自身のservice workerがキャッシュしているので、入れておいた写しは回線を抜いたままでもRAWファイルをスタックします。

**自分で確かめてください。**以上のどれも、鵜呑みにする必要はありません。このページは、リポジトリにあるテンプレートと設定から、誰でも読んで実行できるビルドスクリプトが生成しています。その結果は`dist`ブランチに置いてあるので、配信されているものと、ソースをビルドした結果とを差分で比べられます。 https://github.com/A-Box-of-Tools/website

まず読むとよいのは、Content-Security-Policyについては`config/site.toml`、RAWファイルをメガバイトではなくキロバイトだけ読んでどう開くのかは`src/raw.js`、各手法の計算は`src/stack.js`、そしてページに出るメモリとデコード回数の数字がどこから来るのかは`src/plan.js`です。それらは見積もりではなく、そのファイルの出す答えです。
