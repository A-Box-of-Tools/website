エンコードはあなた自身のブラウザの中で、あなた自身のハードウェア上で行われます。ページがすでに持っているバイト列に対する計算にすぎず、エンコーダーも、サーバーも、省くべき通信の段階もありません。このツールにはネットワーク機能が一切ありません — 取りに行く先も、送る先もありません — 仮に送ろうとしても、このページの向こう側に画像を受け取るサーバーは存在しません。

鵜呑みにする必要はありません。DevTools を開いてネットワークタブを見ながら画像を入れてみてください。画像も、サムネイルも、ファイル名も、選んだファイルの1バイトも、どのリクエストにも載りません。あるいは回線を抜いてからエンコードしてみてください。

この主張をどう確かめられるか

  • 画像には出ていく先がありません。 Content-Security-Policy はこのページが接続してよいアドレスをすべて挙げていますが、そのどれも当サイトのものではありません。あなたのファイルを集めるための受け口はここにはなく、あったとしても送るコードがありません。
  • ここには何かを取りに行くコードがありません。 src/ のどこにも fetch も XMLHttpRequest も sendBeacon もありません。エンコードの実体は btoa と encodeURIComponent — ブラウザが最初から持っている 2つの関数で、どちらもバイト列を受け取ってテキストを返すだけで、どこへも行きません。
  • プレビューが証拠です。 各結果の横に出る画像は、あなたのファイルからではなく、このページがいま組み立てたデータURIから描かれています。表示されるのは、そのURIがサーバーを介さずにあなたの端末で正しくできているからです — もし表示されなければ、壊れたものを渡すのではなく、ページがそう伝えます。
  • メタデータの警告は、あなたの側に立っています。 データURIはファイルをそのまま複製するので、写真の GPS 座標もそれに乗ってスタイルシートへ入っていきます。このページはそれがどれだけあるかを読み取ってお知らせします。そうしなければ、コミットしたあとで気づくことになるからです。
  • Google が読み込むもの、そして渡されないもの。 広告と計測のスクリプトは Google から、寄付ボタンは Buy Me a Coffee から来ています。そのどれにも、あなたの画像に関する情報は渡されません。ファイルを読み、エンコードするコードはすべてこのオリジンから配信され、リポジトリに載っています。
  • オフラインで動きます。 通信を切ってもこのツールは何も変わりません。もともと通信する段階が存在しないからです。これがいちばん単純な証明です。

ご自分で確かめてください。以上のどれも、鵜呑みにしていただく 必要はありません。このページは、リポジトリ内のテンプレートと設定から、あなた が読んで自分で実行できるビルドスクリプトによって生成され、その結果が dist ブランチに置かれています — つまり、配信されている ものと、ソースをビルドした結果とを差分で比べられます:

github.com/A-Box-of-Tools/website

まず読む価値があるのは、Content-Security-Policy については config/site.toml、2種類のエンコードとそれぞれの理由については src/encode.js、メディアタイプを名前ではなくファイルの中身から読み取る方法については src/sniff.js、これから貼ろうとしているもののうちどれだけが画像でないかを調べる部分については src/metadata.js です。

      画像をデータURIに変える手順

      1. 画像を選びます。 選択欄にドロップするか、手で選んでください。ブラウザがディスクから直接読み出します。その間に何かがどこかへ送られることはありません。
      2. 結果をどこへ持っていくかを言います。 URI そのもの、CSS ルール、カスタムプロパティ、<img> タグ、Markdown。どれも URI を引用符で囲んで出します。インライン化した SVG が動くか、黙って動かないかを決めるのは、この細部です。
      3. 代償を読みます。 各結果には、何文字になったか、ファイルよりどれだけ大きいか、そしてこの大きさで埋め込むのは良い考えかが表示されます。 base64 は3分の1を足します。その3分の1がリクエスト1回の節約に見合うかはサイズ次第なので、あなたが線のどちら側にいるかをページが示します。
      4. 警告を確かめます。 画像が EXIF、カラープロファイル、XMP を抱えている場合は、結果の何バイトがそれなのかとともに示されます。拡張子が実際の形式と食い違っている場合は、形式のほうを採用してその旨を伝えます。ブラウザが結果を描けない場合も、そう伝えます。
      5. コピーするか、ダウンロードします。 結果ごとにボタンが1つ、全部まとめて用にもう1つあります — カスタムプロパティは :root ブロックに包まれて出てくるので、スタイルシートの先頭にそのまま貼れます。

      よくある質問

      画像はどこかにアップロードされますか？

      されません。ファイルの読み込みもエンコードも、あなた自身のブラウザがあなた自身のハードウェア上で、ブラウザがすでに持っている2つの関数を使って行います。このツールにはネットワーク機能が一切なく — 何も取りに行かず、何も送りません — ページの Content-Security-Policy は接続してよいアドレスをすべて挙げていますが、そのどれも当サイトのものではありません。

      データURIとは何ですか？

      ふつうウェブアドレスが入る場所に、ファイルまるごとを書く方法です。 url("logo.png") はブラウザに取りに行けと指示するものですが、代わりに url("data:image/png;base64,iVBORw0...") と書けば、そこに画像そのものが入っています。ブラウザはその場で復号します。実際の効果はリクエストが1回減ることです。画像はスタイルシートやページのあとでではなく、それと一緒に届きます。

      SVG が base64 にならないのはなぜですか？

      SVG には base64 が適さないからです。SVG はテキストで、URL はもともとテキストを運べます — 逃がす必要がある文字はごくわずかです。そのわずかだけをパーセントエンコードして残りをそのままにすると、同じファイルの base64 よりだいたい5分の1短い URI ができ、しかもスタイルシートの中で読めるままです。要素名も、色も、viewBox もそこにあり、編集できます。どうしても base64 を要求するツールチェーン向けに、強制するチェックボックスも用意してあります。

      base64 にすると画像はどれくらい大きくなりますか？

      だいたい3分の1です。ファイルの3バイトが base64 の4文字になるので、先頭の data:image/png;base64, を数える前で33%増です。これが下限で、避けられません。URL が許す文字だけで任意のバイト列を書くことの代金だからです。だからこのページは、スタイルシートを配備してから気づくことのないように、ファイルサイズの隣に文字数を表示します。

      画像を埋め込むのが本当に良い考えなのはどんなときですか？

      小さくて、すぐに必要なときです。どのページも読み込むスタイルシートの中の 2KBのアイコンなら明らかに得です。往復が1回減り、CSS が届いた瞬間に画像もそこにあります。10KBあたりを超えると割に合わなくなります。埋め込まれた画像はもはや独立したファイルではないので、単独ではキャッシュされず、ほかと並行して取得されず、周りのファイルが変わるたびに丸ごと再ダウンロードされます — スタイルシートの中の200KBの写真は、サイトのすべてのページのクリティカルパスに200KB足すということです。各結果がその線のどちら側に落ちるかは、ページが示します。

      gzip をかければ base64 の増加分は帳消しになりますか？

      期待されるほどにはなりません。すでに圧縮済みのファイル — PNG も JPEG も WebP もそうです — の base64 は圧縮が効きません。圧縮器が見つけられる冗長性がほとんど残っていないからです。取り戻せるのはたいてい、 base64 が足した3分の1のさらに10分の1程度で、全部ではありません。パーセントエンコードした SVG は逆で、依然としてテキストなので以前と同じくらいよく圧縮されます。SVG を base64 にすべきでない理由が、もうひとつあるわけです。

      画像そのものは変わりますか？

      変わりません。ここにあるほかの多くのツールとの、意図した違いです。ピクセルへ復号して書き直すことは一切ありません。ディスクから読んだバイト列が、そのまま URI に入ります。JPEG は同じ画質、同じ寸法の、まったく同じ JPEG のままです。結果を複製ではなく同じファイルと言い切れるのは、そのためです。

      では EXIF や GPS の情報もスタイルシートに入るのですか？

      入ります。貼る前に考えておく価値があるのがここです。何も再エンコードしないので、カメラが書いたものはすべて画像と一緒に移動します。位置情報も、撮影日時も、カメラのシリアル番号もです。スマホの写真ではそれが30KBに達することもあり、ページのクリティカルパス上で40KBの base64 になり、しかも自宅の住所がリポジトリにコミットされるものの中に入ります。このページは JPEG、 PNG、WebP にどれだけメタデータがあるかを読み取ってお知らせします。先に外すには、EXIF ビューアー & 削除ツール をお使いください。

      ファイルの拡張子と違う種類が使われたのはなぜですか？

      拡張子は間違いうるが、バイト列は間違わないからです。logo.png という名前なのに実際は JPEG として書き出されたファイルは、どの画像ツールも対処しなければならない程度にはよくあります。そして種類を誤って宣言したデータURIは、ただ表示されません — 代替手段も、読む価値のあるエラーメッセージもありません。ですから種類はファイルの先頭数バイトから読み取ります。ここで扱うどの形式でも、そこには曖昧さなく何であるかが書かれています。両者が食い違う場合は、ページがお知らせします。

      プレビューが真っ白です。何が起きたのですか？

      おそらく URI の問題ではありません。HEIC と TIFF はどちらも完全に正しいデータURIになりますが、Safari 以外のブラウザはそれを描きません。ですから貼った先でも画像は出ません — 画像圧縮ツール か 画像リサイズツール で、先に PNG、JPEG、WebP に変換してください。形式がありふれたものなら、ファイル自体が壊れている可能性が高いです。プレビューはこのページが組み立てた URI から描かれるので、真っ白なら画像が復号できなかったということです。

      データURIにサイズの上限はありますか？

      CSS の中や <img> タグの中で行き当たる上限はありません。最近のブラウザはそこに現実的な上限を設けていません。ブラウザが制限しているのはアドレスバーにデータURIを打ち込むことのほうで、いまではたいてい、ごく単純なもの以外は拒みます。この用途とは関係のないセキュリティ上の理由です。本当の上限は上に書いたほうです。技術的に何かが壊れるはるか手前で、そのページはふつうの画像ファイルを使った場合より遅くなっています。

      無料ですか。アカウントは必要ですか？

      無料です。アカウントも、ログインも、試用期間も、透かしもありません。ファイルの数にもサイズにも制限はありません。その費用を払うサーバーが存在しないからです — 処理はあなた自身の端末で起きています。このサイトには広告があり、それが費用を賄っています。広告にあなたの画像に関する情報が渡されることはありません。

      オフラインでも動きますか？

      動きます。ページを一度読み込んでから通信を切っても、そのまま使えます。これは、何もアップロードされていないことを示すいちばん簡単な方法でもあります。エンコードのために画像をどこかへ送っている道具なら、線を抜いた瞬間に止まるからです。

      詳しい解説
